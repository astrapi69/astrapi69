# Releases

Read on demand; the rules every session needs are in core/.

- Start a release by showing the maintainer the state (tags, commits since the last tag, versions) and the SemVer version you propose with its reason, and wait for his OK. (AG-110)
- Never ship with end-of-life dependency versions, with versions facing a forced migration within six months, or with versions that have known unpatched critical bugs. (AG-111)
- Fix every known bug before every release, including those found while cutting it, each with a test red before green; the P label only sets the order and is never a reason to defer. (RL-057)
- List the open issues before the release branch: fix every bug in the cycle, and name every improvement moved to the next milestone in the release PR with its reason; never pass open issues silently. (RL-058)
- Release a change of a documented contract as a major; it stays in a minor only by the maintainer's decision once no family caller is affected (sources, code search, jar bytecode), with a CHANGED BEHAVIOUR bullet. (RL-060)
- Version by SemVer, also in 0.x: feat is a minor, fix, perf and refactor are a patch, a breaking change is a major (in 0.x usually a minor) and is called out prominently in the CHANGELOG. (RL-061)
- Release only at a logical boundary, never in the middle of a feature. (RL-062)
- Freeze the repository from the start of a release cut until it is tagged and published: no other merges to develop, no new PRs or code, only the release work and a fix that blocks the release itself. (RL-063)
- Keep one hand-edited version field per project and derive every other version; a version literal in a derived place means the derivation is broken, so fix the derivation, never the literal. (RL-064)
- Bundle patch and minor bumps and test or build majors (with before/after test counts) into a release; a runtime major gets its own session with migration notes; a security release takes no build or release path change. (RL-065)
- Before a quality-raising release line (mutation tests, parameterized tests, reproducible build, new README), check a repository's classes for JDK or widely used library counterparts and who in the family uses them. (RL-066)
- Measure that use, production and test code apart (public signatures, local checkouts, code search, published jar bytecode), and hand the maintainer a table to decide first: go on, last major with deprecation, or replace. (RL-067)
- Let the release PR write the CHANGELOG entry from the collected bullets: it replaces an unreleased draft or SNAPSHOT header instead of going above it, folds in what that said and removes the draft heading. (RL-069)
- Name the release commits 'docs: changelog for vX.Y.Z' and 'docs: post-release documentation vX.Y.Z'. (RL-070)
- Write the CHANGELOG for humans: groups in the order Breaking Changes (when needed), Added, Changed, Deprecated, Removed, Fixed, Security, commits on one feature collapsed, never raw commit messages. (RL-071)
- Run the full local pre-tag verification for a release cut, every command of its list; the everyday test run does not replace it, even where CI otherwise carries the full gate. (RL-072)
- Tick a checklist item for a test or publish run only with evidence from this session: the run's id and its passed and failed numbers. (RL-073)
- Release nothing that resolves a SNAPSHOT anywhere in its dependency tree (every configuration, test scope and build script included) or has a milestone, RC, alpha, beta or preview version on its runtime classpath. (RL-074)
- Replace an unpublished sibling version by the last published one at the cut, and let the release gate check for SNAPSHOT and pre-release versions before every tag, failing closed. (RL-075)
- Run a family library's release gate except PIT locally on the gated commit: tests, JaCoCo, class file version, no SNAPSHOT, javadoc and a build against an empty local Maven repository. (RL-076)
- Take the release gate's PIT score and floor from the CI mutation testing run on the gated commit, with the run link and proof that the run's tree equals the tag's tree. (RL-077)
- Check before every tag in the library chain that the gate ran on JDK 25 (source compatibility 25, workflows on 25, class files major 69); otherwise move the library to JDK 25 and Gradle 9 as a new major first. (RL-078)
- Before publishing an upstream library, build its consumers against it: publish it to the local Maven repository, point the downstream at that exact version, and release only when its clean build is green. (RL-079)
- Build a change to an upstream library into its consumer locally before proposing it, and report what the downstream run said before asking. (RL-080)
- Release the family's library chain upstream first (crypt-api, crypt-data, mystic-crypt), and push a downstream release commit only when the upstream version resolves on Maven Central. (RL-081)
- Prepare a release from develop, build the shipped artifacts and checksums from the merged release PR, and tag exactly that commit; never tag by hand in a mid state. (RL-082)
- Ship exactly the verified artifacts: never rebuild for publishing, count pending CI as not green, and keep the GitHub release a draft until every station is green and its assets equal the expected set. (RL-083)
- If the publishing run of a pushed tag fails, fix it on the branch and re-run the workflow on the same tag; a tag that cannot ship stays as a record, named in the notes of the release that ships. (RL-084)
- Where a tag push publishes, decide before tagging whether to upload, since a manual Central upload after the tag is a second one, and update the record of what publishes whenever a publishing workflow changes. (RL-085)
- Before pushing a historical release tag, read the publishing workflow at that commit; if it would publish, disable it, push the tag, check that no run started, then enable it again. (RL-086)
- Run a changed publishing workflow once against the snapshot target before a release depends on it, and verify the snapshot's signatures; a repository's first snapshot upload proves its token before its first release. (RL-087)
- Treat a release as unpublished until Maven Central serves the pom, the jar and their .asc files and gpg --verify reports VALIDSIG of the signing subkey; a green tag or publish run proves neither. (RL-088)
- Leave the Central Portal approval to the maintainer; publish the GitHub draft release yourself after verifying the artifacts on Central, in the order tag, approval, verification, draft published with the CHANGELOG text. (RL-089)
- Give each family repository a README 'Releasing' section that names the master step, at its next release. (RL-092)
- Branch a hotfix from the tag it patches (hotfix/X.Y.Z), tag its head, move master onto it, then merge the whole branch into develop (no cherry-picks); a hotfix never changes the build, release path or a persisted format. (RL-093)
- After a release, build the tag locally and compare it with Maven Central: every published artifact is bit-identical. (RL-094)
- Open the next cycle in the same session as the tag by setting the version to the next one with a -SNAPSHOT suffix. (RL-095)
- After a release, check the CHANGELOG links, mark released roadmap items, act on the waiting entries the tag unblocks, update CLAUDE.md if the architecture changed, and record release pitfalls as lessons. (RL-096)
- Class a data format change that older versions read only in part as a minor while the new version reads all older data, and name what older versions lose in the release notes' compatibility section. (RL-097)
- Follow the release workflow step by step and check off its whole checklist; skip a step that is no safety item only on the maintainer's explicit request, and record why in the private chat journal. (OC-002)
- Tag in the shape the project already uses, RELEASE-<projectVersion> in the Java family and the project's own form elsewhere (such as vX.Y.Z); never retag past releases into a new shape. (OC-006)
