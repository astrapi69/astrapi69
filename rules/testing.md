# Testing

Read on demand; the rules every session needs are in core/.

- Make the error reproducible and understand its cause before fixing it; the commits of the fix take the form RL-002 gives them. (RL-006)
- Change code in this order: read and understand its existing tests, write the failing test, implement, keep the suite green, commit, push and open the PR. (RL-007)
- Prove that a test bites with a counter-run: break the code under test on purpose, watch the right test fail, then revert. (RL-008)
- Write at least the happy path and one error case for a new method or function (one happy-path test for a new endpoint), and aim at four tests for a feature or fix: reproduction, happy path, edge cases, boundary values. (RL-009)
- Put edge and boundary cases with the same assertion logic into one parameterized test with a speaking name per case; no copied test methods, no if-cascades on the parameter, and a case with its own setup is its own test. (RL-010)
- Write no test just for the count: every test asserts a real behaviour property, ideally paired with its negative case. (RL-011)
- Skip test-first only for pure documentation, configuration without logic, mechanical refactors covered by the existing suite (which stays green), and visual or device-only aspects, which are checked by hand. (RL-012)
- Name tests after the behaviour they check, not after the implementation. (RL-013)
- Test a tool through the interface it really uses: build real throwaway fixtures (temporary git repositories, key stores, files), call it as the application does, and mock only external services, never calling them. (RL-014)
- Derive a repository's root from the working directory (git rev-parse --show-toplevel), never from a script's own path. (RL-015)
- Use a real in-memory database in integration tests instead of mocking the database layer, and give each test a fresh one. (RL-016)
- Build a consumer's fixtures from the producer's real output (its actual shape or its test factories), and never derive a fixture's expected value from the module under test. (RL-017)
- Reset shared mutable state that several tests see (caches, module globals, singletons) in both setup and teardown of every fixture touching it, or document why it may leak. (RL-018)
- Generate passwords in tests per run, never as literals; the only exception is a checked-in fixture's password, kept with its reason. (RL-019)
- Assert content, not a stand-in: for 'erased' hold the buffer across the operation and assert it is zero-filled, for 'written' read the file back. (RL-020)
- Test round trips of a format: import, edit, export again and diff the result against the original input. (RL-021)
- Add tests by kind of change: unit, integration and (with UI) end-to-end for a new feature, more tests where a refactoring lowers coverage, a migration test and a serialization round trip for a data model change. (RL-022)
- Test an install script or packaging change through the built artifact the way users run it (downloaded, standalone, outside the checkout); a run from the source tree is only a pre-check. (RL-023)
- Test both installation paths at gate time when the same code installs two ways; verifying one does not verify the other. (RL-024)
- Run a reproduction that changes data inside the test harness with its isolation, never as an ad-hoc script. (RL-025)
- Treat a test that fails deterministically on unchanged code as stale, not flaky: rerun it alone, time it, check that the asserted element still exists and read the spec's history before adding retries or timeouts. (RL-026)
- When a feature is removed or changed by design, update or delete its tests in the same change, aligned with the intended behaviour. (RL-027)
- Before implementing a heuristic, detection rule, threshold or prediction about data shape, run it against real data, report counts and sample cases, and treat the spec as a hypothesis. (RL-028)
- Treat a recurrence as its bug class reopened: say so in the issue, link the chain and extend the original tests until the whole class is pinned. (RL-029)
- When a read and a write start from the same action, change the action instead of adding a wait; a value from live data is ordered only within one run, so pin its source across runs. (RL-030)
- Keep end-to-end text assertions locale-robust: match a pattern or a stable untranslated signal (test id, state, count), never one locale's wording. (RL-031)
- Never commit a focused test (such as test.only). (RL-032)
- Never weaken the full (nightly) suite to make a selective PR run green; debug the selection mechanism instead. (RL-033)
- Never remove a safety tripwire such as a production marker to make tests pass; find out why a test pointed at production. (RL-034)
- Read test counts from the test result files, not from the build result: a class that reports fewer tests than it declares never ran them. (RL-035)
- Prove a pure build or dependency change in its PR with class and test counts that are equal before and after. (RL-036)
- Give every gate five tests: it catches the violation, passes on a clean tree, fails closed without its basis, reports what it measured, and its number means the same everywhere (named tolerance for unavoidable variance). (RL-037)
- In a repository with a manual test plan, update it in the same PR for every user-visible change, in all its languages kept in sync; 'not requested' is no reason to skip it. (RL-038)
- If the test plan update would blow up the PR, file an immediate follow-up referenced from the PR; never a silent 'later'. (RL-039)
- Never reuse or renumber test plan ids: a deleted case keeps its number retired, a reworded one keeps its number, a case that becomes a different one gets a new number. (RL-040)
- Leave the test plan alone only for internal refactorings, infrastructure or CI changes, docs or rules fixes and bug fixes without a new user path, but correct a step that described the bug in the fix's PR. (RL-041)
- Never regenerate visual baselines to cover a diff that shows a real bug, and review every changed baseline image one by one instead of accepting regenerated ones. (RL-043)
- When creating or repairing a visual baseline, check once that the reference shows what it claims; a 0-diff run proves only the surfaces in its motif set, so a new tab or panel needs its own motif. (RL-044)
- Treat a 0-diff after an intentionally visible change as a finding: check that the change exceeds the tolerance before labelling it visually unaffected. (RL-045)
- Look at the rendered application after a style change, not only at the names. (RL-046)
- Aim at meaningful coverage, not 100%: assertions on real behaviour and regression pins for known bug classes count more than line count. (RL-047)
- Run a focused coverage and gap audit over the changed area after a major feature phase and before a release, and a full one on request or on a schedule the project sets. (RL-048)
- Structure a coverage audit as a coverage map per test level, a prioritized gap list and statistics with baseline, current value, a +N delta per suite and the gaps closed since the last audit. (RL-049)
- Copy the previous audit report to a dated history file before overwriting it, never edit history files, and update the current report as soon as a session closes gaps. (RL-050)
- Forbid local mutation testing in every brief and workflow prompt, and say how the CI result is read (job summary, report artifact). (RL-051)
- Give surviving mutants in critical code (cryptography, data formats, key handling, services) tests at once; ignore or document them in trivial code (formatting, logging). (RL-052)
- Kill a mutant that survives a weak assertion by sharpening the assertion, never by excluding the mutant, and document every survivor that cannot be killed with its reason. (RL-053)
- Set how often mutation testing runs per repository, always in its CI workflow and never locally; the family has no common cadence. (OC-004)
- Run a heavy coverage run only in CI, and locally only on request; a cheap floor stays in the everyday local gate, such as the JaCoCo floor in check of the Java libraries. (OC-005)
